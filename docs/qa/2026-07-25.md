## Process note — one unintended production call

Check 8d asks for `/court`. I fetched the **page** (200), but I *also* called the `hunt-claim-court` **function** with `?mode=read`, assuming that parameter made it read-only. It does not — that function has no read mode, and my GET ran a full pass: 316 fire-evals, 3 fires asserted, 37.3s.

**Blast radius: zero rows.** The fire insert is an idempotent upsert on `onConflict: claim_id,state_abbr,fired_at` with `ignoreDuplicates: true`, and `fired_at` is pinned to a deterministic `yesterday` rather than `now()`. I verified directly: `hunt_claim_fires` holds exactly 3 rows for `fired_at=2026-07-24` (NC, GA, AL), all with `created_at` of 09:00Z — the cron's own run. Nothing was created at 12:35Z, and `graded: 0` means no grades were written either.

Still a real violation of the read-only guardrail, and the lesson generalizes: on this codebase a GET to a `hunt-*` cron function is a write. Future runs should read `/court` and the underlying tables only, and never invoke a cron function to inspect it.
